# 续聊历史存储优化

## 目标与范围

统一 Responses 续聊需要恢复之前的消息、工具调用和上游不透明内容。历史目前按每个响应保存完整数组，长对话可能反复存储前文。本方案保留完整语义，按调用方、公开模型和入口隔离消息块；相同范围的相同消息复用块，每个响应另存有序摘要。较大消息块使用无损压缩，读取时验证长度和摘要。原生透传的归属、权限、预算和日志保留规则不变。

## 运行方式

程序启动时创建新增的 `conversation_history_blocks` 和 `conversation_history_manifests` 表，始终能读取旧 `kv` 历史和新格式。默认继续写旧格式。设置进程环境变量 `XHUB_COMPACT_HISTORY=1` 后，新产生的统一 Responses 历史使用新格式；移除开关后新写入回到旧格式，已生成的新格式仍由支持它的版本读取。开关是进程级配置，变更需重启进程。

试点时使用 `XHUB_COMPACT_HISTORY=canary`，并将已核验的 XHub 用户 ID 以逗号分隔写入 `XHUB_COMPACT_HISTORY_USER_IDS`。控制台会话和个人 API Key 按网关鉴权后的用户 ID 命中。名单缺失或为空时保留旧写入格式。灰度前让所有网关实例先升级到可读取两种格式的版本；核对灰度账号及对照账号的 JSON/SSE 续接、数据库写入体积和读取延迟，再决定是否扩大范围。将 `XHUB_COMPACT_HISTORY` 设为 `0` 并重启可回退新写入，既有压缩历史仍可续接。试点期间无需迁移或删除既有历史。

所有处理同一批流量的网关使用相同模式和名单。模式值去掉首尾空白后区分大小写，`1` 表示全量并忽略名单，未知值退回旧写入并在首次处理对应请求时记录一次诊断。缩小名单只影响后续请求。同一个响应键被旧格式重新写入时，数据库事务会移除该键的新格式索引，内容块仍留在表中。当前不会自动回收失去引用的内容块。

内容块与索引在同一事务提交。响应历史或归属保存失败时，统一 Responses 不发布成功终态；已有数据帧的流将收到失败事件。固定上游归属和认证隔离仍由现有路由计划检查。历史块缺失、压缩错误、摘要错误或范围不符时，续聊明确失败，不使用旧副本掩盖故障。

## 旧历史迁移

旧键是包含调用方等信息的不可逆摘要，无法可靠恢复跨响应的原始隔离范围。迁移器因此给**每条旧记录**单独设置范围，保留旧副本并逐条重建验证；它不会因为会话名称相同而合并不同旧记录，也不会自动删除历史。这个保守迁移仅带来单条内部去重和压缩，不能声称消除旧记录之间的重复内容；完成迁移前后磁盘占用可能增加。对新产生的响应，同一隔离范围内的块可跨响应复用。

确认全部运行实例都具备新格式读取能力，且已有独立恢复验证的完整备份，才能执行一批：

```sh
XHUB_DATABASE_URL="$YOUR_DATABASE_URL" go run ./cmd/history-compact --execute --confirm-no-legacy-writers --limit=50
```

工具打印 `migrated` 与 `next`；需要继续时将上一批 `next` 传给 `--after`。重新从空游标开始会跳过已迁移记录。运行中断或出错时保留旧副本；失败信息不包含正文或数据库地址。`--confirm-no-legacy-writers` 是操作人确认，不自动检测其他实例。旧版本继续写入时会让新副本过期，因此禁止在混合版本中迁移。该工具不清理旧记录或孤立内容块。

## 验收与回退

先在隔离环境验证中文、英文界面的请求流程，真实 PostgreSQL 的 JSON/SSE 续接、工具调用、身份隔离、并发、错误处理和迁移重跑；测量存储占用、写入/恢复耗时以及迁移过程的磁盘余量。测试上游使用合成数据，不需要生产凭据。合成样本节省率不代表线上效果。

发布时先让所有实例支持双格式读取，再决定是否启用新写入。关闭开关只能改变之后的写入；已经创建的新格式仍需要兼容读取，因此不能直接回退到不认识新格式的旧二进制。旧记录暂不删除。最终清理前需验证完整恢复、引用关系、空间预算和数据库维护方式；普通 PostgreSQL vacuum 主要回收可复用空间，不保证立即归还文件系统。

## 协议容量统计与旧会话压缩预估

运维可在已有 schema 上以只读数据库账号运行以下命令。连接配置从 `XHUB_DATABASE_URL` 读取。命令不初始化表。为每套部署指定稳定且唯一的 `--deployment` 值，再对同一 schema 连续取两次快照。

```sh
go run ./cmd/storage-report snapshot --deployment=primary --days=7 > first.json
go run ./cmd/storage-report snapshot --deployment=primary --days=7 --baseline=first.json > second.json
```

`routes` 用 UTC 请求日、入站和出站协议、显式透传及流式标志归因，给出调用数、诊断字段、内嵌正文和独立采集字段的字节数。字段大小按 PostgreSQL 当前压缩后的存储大小计算，空字段记零。未关联用量的采集按采集日期计数，流式状态为 null。覆盖从窗口第一天零点至采样时刻。旧历史按创建日和种类统计，无法还原的维度保持未归因。块和清单没有创建时间，列在 undated。

`physical_bytes` 给出数据库大小和各类主表、TOAST（含自己的索引）及主表索引大小。只读角色具备查看 WAL 目录的权限时也返回整个 PostgreSQL 实例当前的 WAL 文件大小。两个快照的 `physical_delta_bytes` 表示净变化，可为负数。按创建日期归因的现存字段字节与两个快照间的物理差值独立解读。宿主机上可按需指定 `--backups-dir`、`--container-logs-dir`、`--redis-dir`、`--billing-spool-dir` 或 `--images-dir`，以同一文件系统的已分配块计量。比较时应在同一宿主机上使用同一组目录。报告只输出分类名。

```sh
go run ./cmd/storage-report plan --before=2026-11-19T00:00:00Z \
  --rows=100 --batch-bytes=33554432 --record-bytes=16777216
```

`plan` 只访问早于指定秒级截止点、具有已知格式摘要键及 UTC 创建时间的旧历史。每批先查元数据，再读取预算内的正文，逐条 Zstandard 试压并按原长度和 SHA-256 验证。每个候选默认预留 1 KiB 行与索引开销，可通过 `--reserve-bytes` 调整。单条过大和已有清单的记录只计数。无法识别的旧键或创建时间可在容量快照中核对。按 `has_more` 和 `next_cursor` 续跑，同一批次失败时沿用上一成功游标及原截止点。各批次拥有各自的一致快照，实际转换时还须重新校验原值。

`estimated_selected_savings_bytes` 仅表示按当前假设试算的字段收益。临时新写入空间还需计入并存旧副本、TOAST、WAL 和回滚余量；生产文件系统回收量须通过隔离转换和回收实测。

试算比较旧正文目前经 PostgreSQL TOAST 压缩的字段占用与整条记录的 Zstandard 帧。`history-compact` 按消息拆块、去重并写清单，两种策略各自计量。只读工具允许 `--days=1..31`（默认 7）。`--before` 是精确到秒且已经到达的 RFC 3339 时间。每批默认 100 行（1–1000），原文默认 32 MiB（最大 256 MiB），单条默认 16 MiB（最大 64 MiB 且不超过单批）。每条预留默认 1 KiB（上限 1 MiB）。将 `next_cursor` 原样传给下一批的 `--cursor`，以 `has_more=false` 结束。最后一批可保留非空游标。

协议盘点会访问时间窗对应的用量和采集。缺少独立时间索引的大库可能顺序扫描，单条语句超时为 15 秒。物理差值只比较两次都可见的类别，可选项缺失表示未观测。目录参数应提供真实挂载目录。旧键无法归类和创建时间未知分别统计。
