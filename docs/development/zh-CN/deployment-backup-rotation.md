# 部署备份盘点与轮换

数据库恢复点与部署配置属于不同的回退资源。完整 PostgreSQL 归档提供某一时刻的数据版本。部署配置记录 Git 提交、镜像摘要、Compose 配置、代理配置和可访问的密钥版本。发布记录应关联适用的数据库恢复点。

## 控制每次发布增加的备份

应用和当前数据库经验证可双向兼容时，常规发布可复用原有的数据库备份计划。每次发布记录新旧镜像摘要、回退配置、经过恢复测试的最近数据库备份及其恢复时点。代码回退演练应确认原版本可连接升级启动后的数据库，并保留期间正常写入的数据。归档应包括恢复需要的配置版本和安全访问方式。

出现数据库结构修改、数据回填、删除、版本升级，或无法确认旧程序兼容时，为本次发布建立独立恢复点。完整归档或有连续日志的时间点恢复均需经过验证。注意旧备份的数据时点早于发布时，在恢复时可能丢失两者之间的写入。持久账单队列也需单独核对。

## 本地只读盘点

```sh
python3 scripts/deployment_backup_plan.py --root "$BACKUP_ROOT"
python3 scripts/deployment_backup_plan.py --root "$BACKUP_ROOT" --inspect-limit 8
```

工具查看根目录下每个部署备份目录中的已知归档文件。第一条只查文件元数据，第二条用 `pg_restore --list` 最多检查八个归档的目录项。使用能读取归档版本和压缩格式的 PostgreSQL 客户端。归档目录项中的用户、Key、组织、用量、续聊存储表都有数据入口时，文件会被标注为候选完整备份。结构、账号等部分快照单独保留。目录项检查之后仍需做实际恢复测试。

输出避免显示正文、数据库地址或外部存储位置。总计按设备及 inode 去重，反映已知归档占用的分配块。部署目录其他文件、未识别的布局、文件系统压缩或快照会影响空间对账。最近备份按归档修改时间估算，轮换时需核对实际恢复点。

## 恢复证明和轮换候选

先将归档保存到独立故障域，校验该副本的 SHA-256，再以副本在隔离数据库中完整运行 `pg_restore --exit-on-error`。核对结构、关键行数和金额、账号归属和续聊读取，并记录耗时与恢复点。将验证人员维护的证据保存在单独的只读目录。证据文件名为 `<部署目录名>.<归档文件名>.json`，所需字段如下。

| 字段 | 来源 |
| --- | --- |
| `snapshot`、`archive`、`bytes` | 部署目录名、归档文件名、归档字节数 |
| `sha256`、`offsite_sha256`、`restored_sha256` | 本地归档、独立存储已读回的归档以及完整恢复使用的归档分别实测的 SHA-256 |
| `restore_scope`、`restore_validated` | 完整恢复成功且验证通过后记录 `full_database` 与 `true` |
| `offsite_reference`、`restored_at` | 经核对的外部留存版本引用及带时区的恢复完成时间 |

```sh
python3 scripts/deployment_backup_plan.py --root "$BACKUP_ROOT" --inspect-limit 8 \
  --proof-dir "$BACKUP_PROOF_DIR" --verify-limit 4 --keep 3
```

工具最多重新散列四份本地有证明归档，可能带来较大顺序读取。在低峰或快照上运行。外部副本及恢复证明由操作人员从独立环境核实，命令读取现有证据并匹配本地字节。最近三份完整候选和通过 `--pin` 指定的目录受到保护，并需保留至少一份已核验的本地备份。只有更老且独立复制及完整恢复证据匹配的归档，才会列为人工复核候选。核对备份的实际引用、外部副本持续可用和组织保留要求后再决定轮换安排。命令只输出建议。
